Welcome to Exchange Radar, your gateway to real-time trade data from major cryptocurrency exchanges.

### Supported Exchanges
Exchange Radar currently supports the following top exchanges by reputation and trading volume:
- Binance
- Coinbase
- Kraken
- KuCoin
- OKX
- Bybit
- Bitstamp
- MEXC
- HTX

### Build & Run
Get started effortlessly:

Before starting either stack, copy
`compose/rabbitmq/rabbitmq-definitions.example.json` to
`compose/rabbitmq/rabbitmq-definitions.json` and replace both password-hash
placeholders with hashes generated by `rabbitmqctl hash_password`. The `trades`
password must match the credentials in the stack's `.rabbitmq` environment file.
The populated definitions file is ignored by Git; existing installations retain
their local copy.

#### Locally

    # Start all services (all crypto-exchange producers, consumer and web services)
    $ docker compose -f local.yml up --build -d

    # Start crypto-exchange OKX producer, consumer and web services
    $ docker compose -f local.yml up --build consumer producer-okx

#### Production

    # Start all services
    $ docker compose -f production.yml up --build -d

    # Scale the consumer service horizontally with 2 instances
    $ docker compose -f production.yml up --build --scale consumer=2

### Production recovery

Every production service uses `restart: unless-stopped`, including both replicas
of the consumer. Running containers recover after Docker or the VM restarts.
Services stopped manually stay stopped until explicitly started again. A restart
policy does not prevent the brief interruption caused by a Docker update.

After pulling this configuration, an existing installation can adopt the policy
without rebuilding images, replacing containers, or restarting services:

```bash
docker-compose -f production.yml ps -a -q |
  xargs -r docker update --restart unless-stopped
```

This command includes stopped containers. Updating the policy does not start a
stopped service. To recover the existing stack while preserving its containers,
volumes and consumer replica count, use:

```bash
docker-compose -f production.yml start
```

For a VM using Docker from Snap, schedule updates in a maintenance window and
verify website availability afterwards. The following administrator command
sets the **system-wide Snap** update window to 02:00–03:00 in the VM's timezone:

```bash
sudo snap set system refresh.timer='02:00-03:00'
snap refresh --time
```

The Radar VM uses UTC, so this is 03:00–04:00 in Amsterdam during winter and
04:00–05:00 during summer. This setting retains automatic updates and does not
start an update immediately. The existing website uptime monitor provides outage
alerts; no additional monitor is installed by this change.

### Price alerts

The scheduler generates alerts for price changes of at least 1% between its
one-minute checks or 2% between its ten-minute checks. The alerts page polls the
web API every two seconds; it does not generate alerts itself.

Scheduler exchange lists are configured separately in `.envs/.production/.scheduler`.
The current alert list is BTC, ETH, LINK and PEPE. Remove EQTY, FTM and S from all
exchange lists in that file before recreating the scheduler. This production
configuration is not tracked by Git, so pulling code alone does not update it.

Missing or invalid coin statistics skip only that coin. Its previous comparison
is discarded, so the next valid check starts a new interval rather than reporting
a change accumulated during the data gap. Other coins continue to be evaluated.

### Retired pairs

EQTY and S are no longer collected or shown in the UI. Production environment
files are not tracked by Git. Remove `SUSDT` and `SBTC` from Binance's list and
`S-USDT` from the KuCoin and OKX lists in `.envs/.production/.producer`; remove
`S` from the exchange lists in `.web` and `.scheduler` as well. Recreate the
affected producers and rebuild/recreate the web service to apply these changes.
Clear the retired coin's Redis records only after its subscriptions have stopped,
so new trades cannot recreate the data.

### Binance ingestion

Binance uses one public trade WebSocket per symbol, with automatic protocol
ping/pong handling. Readers retain raw JSON bytes in a shared burst inbox instead
of blocking behind the SDK's additional 5,000-message queues. The inbox accepts
up to 50,000 trades or 16 MiB of payloads, whichever comes first, including the
batch being published. Queue objects and parsed models add memory beyond this
payload budget; it is not a limit on the process's total memory. Individual
WebSocket messages are limited to 64 KiB.

A single worker builds models, updates Redis statistics and publishes each trade
over AMQP. It uses batches of 50 normally and 200 when at least 200 trades are
already waiting. Partial batches flush after at most 20 ms of collection time.
Every trade keeps its own cumulative statistics and existing alert routing.

A batch uses one atomic Redis script call instead of four network round trips per
trade. The worker retains a failed batch for retry before processing later trades;
trade IDs prevent repeated statistics updates, and the latest batch response is
cached for one hour to recover a lost Redis reply. Socket errors retain the capped
60-second reconnect backoff. A full inbox logs an explicit warning and reconnects
the affected stream while retaining previously accepted trades. Sustained
overload can still lose trades once these finite limits are reached. Buffered
trades remain in memory: process restarts or long outages can also lose trades,
and interrupted RabbitMQ publications can produce duplicate deliveries.

A throughput log appears once per minute while trades are being processed, with
received/processed counts and rates, queue depth, payload bytes, peak backlog,
event-loop delay, and the age of the completed batch.
A queue that keeps growing indicates the producer is still falling behind. Adding
consumers helps only when the downstream RabbitMQ queues are backing up.

The socket burst regression tests use real WebSocket connections against a local
server, including 40,000 simultaneous trades with publishing stalled and protocol
heartbeats still active; no Binance API access is needed.

The Redis integration tests are opt-in. Set `TEST_REDIS_URL` to a reachable test
Redis instance when running pytest. Tests use unique key prefixes and remove only
their own keys.

### Consumer delivery

Producers send trades to the existing RabbitMQ queues over AMQP. Each consumer
collects up to 50 deliveries per queue, or waits up to 20 ms for a partial batch,
and forwards the batch over a reused HTTP connection. All four feed categories
use their existing endpoints with `_batch` in place of the coin, for example
`POST /api/feed/_batch` and `POST /api/feed/_batch/whales`.

The web service processes each trade in batch order, using its own `trade_symbol`
for browser delivery and the existing persistence rules. Single-trade requests
remain supported. Batch responses include `accepted`, the number of processed
trades; consumers acknowledge messages only after receiving the complete count.
An older web service cannot confirm this receipt, so new consumers retain their
messages until the web service is updated.

Prefetch bounds each consumer's unacknowledged deliveries to 50 per queue. Failed
HTTP batches are retained and retried with a 1–10 second backoff while AMQP
heartbeats continue. A closed broker connection requeues unacknowledged deliveries.
Delivery is at least once: a lost HTTP response or AMQP acknowledgement after
processing can cause duplicate browser deliveries or saved feed entries. Multiple
consumers do not provide global ordering across batches.

Set `TEST_AMQP_URL` to a test broker to run the optional transport integration
tests. They create uniquely named queues and remove only their own queues.

Consumers log delivered-message and HTTP-request counts once per minute while
active. Existing queued trades are retained during deployment. Build both images,
stop the old consumers before replacing the web service, then start two updated
consumers:

```bash
git pull &&
docker-compose -f production.yml build web consumer &&
docker-compose -f production.yml stop consumer &&
docker-compose -f production.yml up -d --no-deps web &&
docker-compose -f production.yml up -d --no-deps --scale consumer=2 consumer
```

### UI
Explore real-time trade information effortlessly:
- Visit http://127.0.0.1:9000/BTC to access real-time BTC trades.
- To track BTC whales' transactions, navigate to http://127.0.0.1:9000/BTC/whales.
- For BTC dolphins' transactions, use http://127.0.0.1:9000/BTC/dolphins.
- To monitor BTC octopuses' transactions, head to http://127.0.0.1:9000/BTC/octopuses.

Feel free to replace BTC with any other supported coin across the exchanges.

### Hardware Requirements
Exchange Radar operates efficiently without requiring extensive resources. In fact, all services run seamlessly on a single Raspberry Pi 4.
